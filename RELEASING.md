# Release walk

Nothing publishes to npm until one packed-tarball walk has passed on the exact commit the release PR would ship. Each release's Phase gate issue, filed by `.github/workflows/phase-gate.yml` from `.github/release-checklists/patch.md` or `minor.md`, tracks that walk. This file holds the steps. #673 was the 0.5.1 gate, and its record stays there.

**Scope (operator ruling, 2026-10-21).** A patch release walks only the steps its diff changed, plus a fixed core: step 1 (install), a minimal step 5 to 6 run, and `pnpm gate:side-checks`. Each unchanged step carries forward with git-diff evidence that its files are untouched since the walk that last passed it. A minor release walks every step. Findings go in one `X.Y.Z walk findings` issue, one checkbox per finding with its evidence.

## How the gate works
- The gate attaches to the release PR (`chore(main): release X`) and is keyed to that PR's **base SHA**. release-please opens the PR but publishes nothing until the operator merges it, so the gate blocks the release and never a merge to `main`.
- Anything merged to `main` moves the base SHA: redo the CI lines under **Before the walk** on the new base.
- Failures found during the walk are noted as it goes and filed together as one ticket at the end. A failed step is rechecked once its fix merges.


## Before the walk
- [ ] The release PR's checks are green on its head, `Packed intake` included.
- [ ] `Standalone CLI` dispatched on the base (`gh workflow run standalone.yml --ref <base>`; it runs on no push).
- [ ] `Desktop` on the base. Step 11 takes its artifact from this run.
- [ ] Docs for this release's screens merged in `prismalens/prismalens.io`.
- [ ] The Windows runbook on #634 - U11: breadth matches the build.
- [ ] Lab checks at the start of step 5: Alertmanager stays up while a fault switches on and off, and `task dashboard` answers on :7420.

## What passes the gate
- [ ] Before the release PR merges, one packed session passes on its base SHA, and the transcript is pasted on the release PR.
- [ ] The session uses the `npm-tarballs` artifact of `Pack npm tarball` on the base SHA (never an npm version), a fresh `mktemp -d` workspace and a port other than 6473, and covers in one run the steps the scope above requires.
- [ ] `Standalone CLI` green on every OS on the base SHA: `smoke-installer` covers the upgrade from the previous release, PATH, reinstall, the downgrade guard, a second `pl` on PATH and uninstall.
- [ ] No address grants access (ADR 0004 §8): an unpaired browser on `localhost` gets the pairing page, not the app; a spent or expired link says so; a revoked device is refused on its next request.
- [ ] Telemetry: the first `pl up` on a workspace prints the usage-data notice (what is counted, what is never sent, how to turn it off) and sends nothing; the Inbox shows the notice once until dismissed; on the first start of a UTC day after the notice was shown, Settings → Usage data → Recently sent shows `install_active` with `build`, the install channel in `run_mode`, and a UTC-midnight `timestamp`; a later start the same UTC day sends none and reads "Nothing sent since PrismaLens started."; the Settings switch, `pl up --telemetry=off`, `PRISMALENS_TELEMETRY=off`, `DO_NOT_TRACK=1` and `CI` each stop it, and the switch shows the override.
- [ ] Update notice: `pl up` prints `Run: pl upgrade` only once the newer release's `SHA256SUMS` exists; suppressed under each of non-TTY stdout, `CI`, `DO_NOT_TRACK=1`, `PRISMALENS_UPDATE_CHECK=off` and `PRISMALENS_RUN_MODE=electron`; with none set, the cache file exists and a second boot inside 24 h makes no request. Settings → About and the Settings dot follow the same cache. *To see "available" while the build under test is the newest release, seed the cache before `pl up`: `echo "{\"checkedAt\": $(date +%s%3N), \"latest\": \"9.9.9\"}" > "$PRISMALENS_WORKSPACE_DIR/update-check.json"` (a fresh `checkedAt` means no request; the line shows only under run mode `npm`).*
- [ ] Workspace lock: a second `pl up` on the same workspace is refused naming the holder's pid and port; `SIGTERM` exits 143 and removes the lock; the next boot takes a free lock with no stale reclaim.
- [ ] A reset and a starting investigation refuse each other rather than racing, observed through the API.
- [ ] The two fixtures of #336 - release gate: prove an investigation is useful on three repos we did not write, replayed against this tarball with `scripts/replay-fixture.mjs <fixture> <tarball-dir>` (cards in `scripts/replay-fixtures/`); `checks.json` passes on both, and the plausibility verdict is recorded.
- [ ] **Docs:** docs.prismalens.io describes every command, flag, env var and page this release changed, checked against the packed tarball, with links validated on the built site. The site goes live after the release, once every gate has passed (`publish-docs.yml` publishes after npm has the version).
- [ ] **Phase gate:** a docs sweep for renamed or retired identifiers, and registry-mode `cross-os-smoke` on the published version, linked here.
- [ ] **After publish:** a GitHub Release with narrative notes, carrying the five archives, `SHA256SUMS`, `install.sh`, `install.ps1` and the desktop zips; `prismalens/homebrew-tap` and `prismalens/scoop-bucket` have the version; `brew install` and `scoop install` of it run `pl --version`.


## The walkthrough
The steps describe the UI as of 0.5.1. A release that changes a step updates its text here in the same PR.

The operator at their own desk, an agent guiding one step at a time: a person trying every feature 0.5.x built, not a script clicking. Nothing here is optional. For each step the guide says what to do and what to expect, and records pass or fail with a screenshot or the terminal output.

1. **Install and start.** `npm i -g <tarball>`, then `pl doctor`: version and install channel, every `pl` on PATH, the coding agents it finds and the one it would pick, the git version and this shell's credential helpers (with the note that the background service has its own environment), the webhook URL and who can reach it. `pl up` on an empty workspace prints `Open: …/pair#…`; the browser opens on it and lands on the Inbox (Getting worse, Alerts and Services tiles; Needs you) with no account and no click. Recently resolved appears once an incident has resolved (step 9).
2. **Devices.** Settings → Devices lists `This machine · <browser>`. `pl up --tailscale-serve` prints the `https://<machine>.<tailnet>.ts.net` address, and `pl pair --tailscale` pairs the phone over it. On the phone: incidents with no sideways scroll, copy buttons that work, no way to pair or revoke. Revoke it from the host; the phone is refused. From the host only, `pl pair --address` refuses an unreachable or unallowed address. Pairing over a LAN address is not a gate item: other devices go through Tailscale.
3. **Agent and model.** The picker is one popover: the agents, then that agent's models by name, with no field for a model id in the picker (Settings → Agent → Custom models has a "Model id for <agent>" field per agent, on purpose). In Settings, "Check readiness" on each installed agent, with `tested <version>` where a row has one; a check on one agent never disturbs another's. An agent that is not set up (not signed in, no key) is disabled in the picker with its reason and cannot be chosen; Investigate refuses it with the same reason; a Windows-side agent on a WSL PATH is reported as the Windows install, not probed. The model is kept per agent.
4. **A service with its code.** A folder source and a git URL; the service shows what git found. Credentials: a private repository clones with this machine's own git, and the service's Code row says so (`Code: machine git (<helper>)`); Settings → Integrations → Add a token saves a Git host token, its Test runs against the saved repositories on that host, and a repository pinned to it shows `Code: token <label>` with the fingerprint on hover; a public repository shows `Code: public`; a rejected token marks its connection in Settings and the clone says what to do next, never prompting or hanging. Dependencies: add an upstream and a downstream link; the reverse link shows on the other service, and, with both links still in place, an investigation on the service gets both in its prompt (`SERVICE NEIGHBOURHOOD` in `runs/<id>/transcript.jsonl`). The service's Impact metric field takes a PromQL expression. After that run, delete a throwaway service: the dialog names the incidents and dependency links it affects, and Cancel leaves it.
5. **Alerts in.** An Alertmanager webhook with the token; a grouped delivery naming two services opens two incidents; a resolved delivery closes its incident; a resolution that arrives before its firing is remembered. Close the lid on a firing alert, resolve it, wait 10 min, reopen, Pull: the incident resolves and the overview's What changed card shows the reason. Connect Alertmanager or Prometheus, then Pull and catch up. A generic webhook delivery and a Render webhook delivery (signed) each open an incident; an unsigned Render delivery is refused. Settings → Alert sources (Prometheus and Alertmanager): add a connection, test it, override it per service, and remove it after reading its impact preview (OAuth deferred to 0.5.2). With Prometheus connected, the overview's Impact card charts the alert's own query over 24 h with its threshold, units and deploy markers; without it, the card offers to connect Prometheus. What changed lists the linked repositories' commits and deploys before the incident. An investigation against that Prometheus cites a query result as evidence.
6. **An investigation.** Start one from a critical alert, from the overview's box with a brief typed in, and from "New conversation" in the runs menu. The incident's runs and questions are listed under it in the sidebar; the box's chips show the run's model, effort and context window, and its access level (Ask always, Auto-accept edits, Auto, Full access; the agent's own default first and tagged; a lock only where a sandbox is proven, else "No sandbox on this machine."). The run page's strip shows the state in words (Starting, Working, Done, Stopped by you, Failed), current activity, the model chip (it warns only when the agent ran another model) and the Code line naming the credential; the transcript shows numbered steps (Ran, Read, Failed) that expand to the full command and output, and `#step-N` opens one. The Run details panel opens beside it with Summary, Evidence (each item links to its step), Context and Steps with filters, and Esc closes it. At Ask always, a write, or a read outside the snapshot such as `cat ~/.bashrc`, shows as an Approve / Deny card naming the call, and the Inbox and sidebar say Waiting for your approval; at Auto-accept edits only non-edit asks show; at Auto and Full access nothing asks. An agent's ask to switch its own mode is refused and shown. Deny refuses it and the run goes on to its report; Approve lets it run. An ask nobody answers is denied before the run's time limit (10 minutes at most) and the card says why. Your own Claude Code allow/deny rules apply: what `~/.claude/settings.json` allows runs without asking, what it denies is refused. An incident whose alerts span two services' repositories gets both in its workspace. Stop from the box (Esc while it has focus) and from the run strip: no confirmation, no toast, the run ends in "Stopped by you" (never "failed"), and no agent process is left behind. An old `/investigations/<id>` link lands on that run.
7. **Talking to a run.** The box talks to the selected run. While it works: Enter queues a message for the agent's next pause and the agent answers in the same thread; a message the run never read shows as not delivered. After it finishes: Continue resumes the same session ("Resumed in the same session, code at <sha>") and the report is unchanged. Ask from the overview starts a question that writes no report and opens as its own conversation; Investigate again starts a new run with the report quoted, including on a finished run that kept no session.
8. **The report.** The overview's Why card shows the newest run's finding, with a link to its transcript; with none, why there is none. The Run details panel's Summary carries the run's facts (status, start, access, agent, model, code) and Evidence its report; pick another run in the sidebar or the runs menu to read its own, and a later report may cite an earlier run by number. Hypotheses in order with their evidence; host facts marked inferred; the model chip names agent and version with no read-only claim, hover shows the model and where it came from, and **model substituted** appears when the agent ran another model; the run strip says the same. Earlier incidents with their actual cause.
9. **After the report.** The Stop the impact card's Next strip: Copy the fix command, "I applied it", Check now, then Not yet / Could not check / It worked, then Resolve. Resolve with an actual cause and category; the header menu's Export as Markdown, Write a status update (logged on the timeline) and Change severity; Slack delivery if configured; the next similar incident shows this one. (Deferred to 0.5.2: post the report to GitHub.) Merge an incident into another open one from the header menu: its alerts move, its timeline stays on it with a link to the survivor, and the survivor's timeline names the merge. Create an incident by hand and add a Note from the box. Reopen a resolved incident from its header (it asks first); "+ New run" on a resolved incident leaves its status alone. A refire of the same alert within 24 h of "Alerts cleared" reopens the incident and starts a new run, or, while a run is still working, its timeline says why it did not; after 24 h, or after Resolve, it opens a new incident whose first timeline entry names the old one.
10. **Operating.** Ctrl-C leaves no processes behind; the usage-data switch and Recently sent in Settings; Settings → About (version, channel, build, update status, `pl upgrade`, workspace, latest backup) and `pl upgrade --check`; the Danger zone's uninstall command, and its factory reset on a throwaway workspace. Analytics' ranges and counts agree with the Inbox and All incidents. `pl service install`, then a `pl upgrade` whose trial fails rolls back to the previous version and database, and `pl service status` shows the outcome on its `Upgrade:` line; `pl service restart` and `pl service uninstall` leave no unit behind. `pl reset`.
11. **The desktop app.** From the `Desktop` artifact, double-click the app: the window opens with no sign-in; each page's header is the title strip, every control in it clicks, and nothing clickable sits under the window controls; the tray shows the running count and has Pair a device, Start at login, Reset workspace and Quit; a notification arrives when an investigation finishes; with `pl up` already running, the app attaches to it. (Deferred to 0.5.2: on macOS, the app menu's Check for Updates and Settings (Cmd+,) work, and the tray offers "Download PrismaLens <version>" when a newer release exists.)
12. **Windows.** The runbook verdict on #634: native Windows (npm, the installer, Scoop; the host has no Scoop yet, so install it first) and WSL2. In the desktop app, the tray's **Run in WSL** with a distro boots PrismaLens inside it; with no `pl` in the distro, a dialog says so.


## Lab
- **Step 5:** the sreforge env (prismalens/sreforge#200 - sreforge becomes a running env for prismalens). `task up` starts booklogr, Prometheus :9090 and Alertmanager :9093; `task fault <scenario> on|off` toggles a fault. On Rancher Desktop the webhook URL is `http://192.168.127.254:<port>/api/webhooks/prometheus`; `172.17.0.1` and `host.docker.internal` don't reach WSL. Scenarios share `BooklogrApiLatencyP99High`: a second fault inside 24 h reopens the first incident with a new run (`PRISMALENS_ALERT_FLAP_WINDOW_MINUTES`, default 1440); set it to 1 for the walk's "new incident naming the old one" check.
- **Step 2:** the operator's phone on the tailnet. Tailscale runs inside WSL (`tailscale up --operator=$USER`), and the tailnet needs MagicDNS and HTTPS certificates on.
- **Step 12:** the operator's Windows 11 host (Node v24.13.0, npm 11.5.2). The guide runs in WSL2 on it and drives native Windows through `powershell.exe`.
